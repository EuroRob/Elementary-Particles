## What changed because of this

The first run of these numbers (2026-11-14) showed about a third of agent commits followed within a week by a fix on the same files, a six-minute median from pull request to merge, and review comments on 2 of 68 pull requests: review happened in the agent session, and nothing ran the tests or any validation automatically. In response, the repository got a Forgejo Actions pipeline on its own isolated runner (`scripts/ci/check.sh`: YAML, Python, shell, Terraform formatting, Ansible syntax, 300 offline tests, secret scan on every pull request) and a pull-request template that asks for what changed, what ran, known risks and what needs a human look. The next recomputation is the test of whether the follow-up-fix rate drops; first-pass validation (did the checks pass on the first push) becomes measurable from the pipeline's history.

## How to read this

- The follow-up-fix rate is an upper bound on rework: it counts any later fix on the same files, whether or not the agent's change caused it. Almost all of those fixes are agent commits too, i.e. the agent iterating on its own work inside the same task; the row below it counts only fixes a person made afterwards, which is the closer measure of defects that got past the session.
- The human-only rate is not a like-for-like baseline: those commits are few, and many are large catch-up commits whose files were touched again later for unrelated reasons. It is shown for completeness, not as a ratio to quote.
- Fast merges reflect a one-reviewer repository: the reviewer is the person who asked for the change and read it as it was produced. The number to watch over time is reverts of agent commits.
- Pull-request figures need `--prs` with an export from the git host's API; the git-only figures work on any clone.
